## 1. 产品愿景与定位

### 1.1 一句话定位

**TasteCraft 是一个 7x24 小时自动运转的 AI 自媒体引擎，通过"品味进化"让生成内容越来越像用户本人，而不是像 AI。**

### 1.2 愿景

让每个人都拥有一个比自己更懂自己品味的 AI 内容团队。

TasteCraft 不是一个"帮你写文章"的工具。它是一个**自主运转的内容引擎**——用户设定方向后，系统自动选题、创作、审核、适配、发布、回收数据、进化品味，7x24 小时不间断。用户的角色从"内容生产者"变成"内容策略制定者"。

### 1.3 核心差异化

| 维度 | 传统工具（易媒/新榜/蚁小二） | AI 写作工具（ChatGPT/Jasper） | TasteCraft |
|------|---------------------------|----------------------------|------------|
| 定位 | RPA + 账号管理 | 按需生成 | 自动运转的内容引擎 |
| 用户角色 | 操作者（手动触发） | 提问者（每次输入 prompt） | 策略制定者（设定方向，系统自动运转） |
| 内容个性化 | 无 | 靠用户写 prompt | 品味进化引擎自动学习 |
| 运行模式 | 用户驱动 | 用户驱动 | 系统驱动（Cron 7x24） |
| 核心壁垒 | 平台数量 | 模型能力 | 用户品味数据资产 |
| 目标用户 | 专业运营（1→10） | 所有人 | 零经验用户（0→1） |

### 1.4 目标用户画像

**P0 用户：创始人/小团队负责人**
- 有产品/业务，需要自媒体曝光
- 没有专职运营人员
- 时间极度稀缺（每天最多 15 分钟花在内容运营上）
- 能接受 AI 生成内容，但要求"不能看起来像 AI 写的"

**P1 用户：个人 IP 打造者**
- 想建立个人品牌但不知道怎么开始
- 试过用 ChatGPT 写内容，发现"千篇一律"
- 需要跨平台分发但嫌手动操作太麻烦

**P2 用户：小微企业老板**
- 需要产品/品牌曝光
- 预算有限，请不起专业运营
- 需要可衡量的 ROI（线索/曝光/咨询量）

### 1.5 核心使用场景

**场景 1：首次使用（Onboarding）**

用户注册 → 5 分钟品味问卷 → 系统建立初始画像 → 自动生成第一篇内容（预览）→ 用户确认/修改 → 发布

**场景 2：日常运转（Autopilot）**

系统每日自动：选题 → 生成 → 审核 → 发布。用户每天收到飞书/微信通知：今日发布了什么、数据表现如何。用户偶尔：看周报、调整方向、审批低置信度内容。

**场景 3：品味进化（Evolution）**

系统每周自动：分析本周数据 → 更新品味画像。用户收到进化报告：哪些风格效果好、哪些需要调整。用户选择：接受系统建议 / 手动微调 / 维持现状。

## 2. 问题分析与市场洞察

### 2.1 核心问题

**AI 生成内容的"千人一面"困境：**

现有 AI 写作工具（ChatGPT、Claude、Jasper、Copy.ai）解决了"写"的效率问题，但制造了一个新问题——所有人用同一个模型，生成的内容风格趋同。用户花 5 分钟生成一篇文章，结果读起来和其他 100 万人用 AI 生成的文章一模一样。

这就是为什么很多人试用 AI 写作后又放弃了——不是因为质量差，而是因为**没有个人风格**。

### 2.2 现状分析（Status Quo）

目标用户当前的工作流：

1. 想选题（手动/灵感驱动，不稳定）
2. 打开 ChatGPT/Claude，输入 prompt，生成初稿
3. 手动调整内容（加入个人风格、调整平台调性）→ 这一步最耗时
4. 手动逐个登录各平台，复制粘贴发布
5. 偶尔看看数据，但无法系统性分析
6. 下次生成时，重新输入 prompt，之前的偏好没有积累

**痛点量化：**
- 步骤 3 耗时：30-60 分钟/篇（手动调整到"像自己写的"）
- 步骤 4 耗时：15-30 分钟（6 个平台逐个发布）
- 步骤 6 的问题：每次从零开始，没有学习曲线
- 总计：每篇内容 1-2 小时，每天最多生产 1-2 篇

### 2.3 竞争格局

```
                    高个性化
                       ↑
                       │
          TasteCraft ★ │
                       │
    ┌──────────────────┼──────────────────┐
    │                  │                  │
人工驱动 ←─── Jasper ──┤── ChatGPT ───→ 系统驱动
    │         Copy.ai  │   Claude        │
    │                  │                  │
    │    易媒/新榜     │                  │
    │    蚁小二        │                  │
    └──────────────────┼──────────────────┘
                       │
                       ↓
                    低个性化
```

**空白象限：** 右上角——高个性化 + 系统驱动。目前没有产品占据这个位置。

### 2.4 为什么是现在

1. **Claude/GPT-4 级别的模型能力**：能理解"品味"这种抽象概念，并在生成中体现
2. **长上下文窗口**：可以把完整的品味画像 + 历史数据塞进 system prompt
3. **Tool use 原生支持**：模型能自主调用搜索、发布等工具，实现端到端自动化
4. **国内自媒体生态成熟**：6 大平台覆盖了 90% 的内容分发需求

## 3. 品味进化引擎 — 核心创新

### 3.1 引擎概述

品味进化引擎（Taste Evolution Engine, TEE）是 TasteCraft 的核心差异化组件。它实现一个持续学习的闭环：

```
品味画像 → 内容生成 → 平台发布 → 数据回收 → 进化分析 → 更新画像 → ...
```

### 3.2 品味画像（Taste Profile）

品味画像是用户品味的结构化表达，分为**显式维度**（用户设定）和**隐式维度**（系统学习）。

#### 显式维度（Onboarding 时采集）

| 维度 | 说明 | 示例 |
|------|------|------|
| 身份与领域 | 用户是谁、做什么 | "AI 产品创始人，关注效率工具和创业" |
| 内容调性 | 整体风格基调 | "专业但不失亲和，偶尔毒舌" |
| 目标受众 | 内容写给谁看 | "25-35 岁互联网从业者" |
| 品味标杆 | 最喜欢的 3 个自媒体账号 | "少数派、虎嗅、阑夕" |
| 禁忌清单 | 绝对不能出现的元素 | "不用'赋能'、不写鸡汤、不用过多emoji" |
| 口头禅/金句 | 个人标志性表达 | "说人话"、"别整虚的" |
| 内容目标 | 希望读者看完后的感觉 | "学到东西 + 想转发" |

#### 隐式维度（系统学习）

| 维度 | 学习来源 | 更新频率 |
|------|---------|---------|
| 最佳标题句式 | 平台数据（高点击率标题的共性） | 每周 |
| 最佳开头风格 | 平台数据 + 用户修改 | 每周 |
| 最优内容长度 | 平台数据（阅读完成率） | 每月 |
| Emoji 使用密度 | 用户修改（增删 emoji 的模式） | 每次生成 |
| 话题标签策略 | 平台数据（哪些标签带来更多曝光） | 每周 |
| 段落节奏 | 用户修改（段落拆分/合并模式） | 每次生成 |
| 平台适配规则 | 各平台差异化表现数据 | 每月 |

### 3.3 Onboarding 流程

**策略优先级：导入已有内容 > 品味问卷 > 赛道模板**

**路径 A：导入已有内容（最强冷启动）**

用户提供 3-5 篇自己写过的内容（任何平台，可以是链接或文本）→ 系统调用 Claude 分析这些内容 → 自动提取品味特征（用词习惯、内容结构、情感基调、话题偏好）→ 生成初始画像 → 用户确认/微调。

**路径 B：品味问卷（5 个问题，2 分钟）**

- Q1: 你做什么的？一句话介绍自己 → 确定领域和身份
- Q2: 你最喜欢的 3 个自媒体账号是谁？ → 系统分析这些账号的风格特征
- Q3: 三段不同风格的开头，选你最喜欢的 → [专业严谨版] / [轻松口语版] / [犀利观点版]
- Q4: 有没有你绝对不想出现在内容里的东西？ → 禁忌词、禁忌话题
- Q5: 你希望读者看完你的内容后有什么感觉？ → "学到东西" / "被逗笑" / "被说服" / "想转发"

**路径 C：赛道模板（兜底）**

| 赛道 | 默认调性 |
|------|---------|
| AI/科技 | 专业但不失亲和，数据驱动，案例拆解 |
| 美食/生活 | 轻松口语化，高 emoji，场景感强 |
| 商业/创业 | 观点鲜明，反直觉，金句密集 |
| 教育/知识 | 结构清晰，深入浅出，实操性强 |
| 时尚/美妆 | 种草体，亲测分享，视觉优先 |
| 健康/运动 | 科学严谨，个人体验，激励型 |

### 3.4 进化信号系统

品味进化依赖三层信号：

**Layer 1：即时反馈（每次生成后）**

| 用户操作 | 信号强度 | 学习内容 |
|---------|---------|---------|
| 直接发布（无修改） | 强正信号 | 当前风格正确 |
| 修改后发布 | 中性信号 | diff = 学习材料 |
| 要求重新生成 | 弱负信号 | 当前方向需调整 |
| 放弃不用 | 强负信号 | 严重偏离品味 |

**用户修改是最有价值的进化信号。** 系统保存生成版本和最终发布版本的 diff，让 Claude 分析修改模式。

示例：
```
生成版本："这个工具赋能了创作者，让内容创作更加高效。"
用户修改："这工具真的好用，写东西快了 3 倍。"

系统学习：
- 禁忌词 += "赋能"
- 偏好 += "口语化表达"
- 偏好 += "具体数字替代抽象描述"
```

**Layer 2：平台数据（发布后 24-72h）**

| 指标 | 说明 | 权重 |
|------|------|------|
| 阅读量/曝光量 | 内容被多少人看到 | 0.2 |
| 互动率 | (点赞+评论+收藏+转发) / 阅读量 | 0.4 |
| 完读率 | 读完全文的比例（仅部分平台提供） | 0.2 |
| 评论情感 | 正面/负面/中性评论比例 | 0.1 |
| 涨粉量 | 因该内容新增的关注者 | 0.1 |

数据采集频率：每篇内容发布后 T+24h、T+72h、T+7d 各采集一次。

**Layer 3：赛道热点（持续监控）**

每周自动执行：搜索用户赛道的近 7 天爆款内容（各平台 top 20）→ Claude 分析爆款的共性特征（标题句式、内容结构、互动策略）→ 对比用户当前画像，找出可借鉴的趋势 → 生成趋势洞察报告。

### 3.5 进化算法

品味进化不是规则引擎，是**让 Claude 作为品味分析师进行推理**。

**进化触发条件：**
- 即时进化：每次用户修改内容后
- 周度进化：每周日 22:00，汇总本周所有信号
- 月度进化：每月末，深度分析趋势变化

**进化约束：**
- 每次最多调整 3 个维度（避免剧烈变化）
- 置信度 < 0.5 的调整标记为"试探"
- 试探性调整需要 A/B 验证：下次生成两个版本，看用户选哪个
- 用户显式设定的维度（禁忌、调性）只能微调，不能颠覆
- 保留完整进化日志，可回溯任何时间点的画像状态

### 3.6 品味进化的护城河效应

```
使用时长        画像精度      迁移成本      竞品追赶难度
──────────     ────────     ────────     ──────────
第 1 天         30%          无            零
第 1 周         50%          低            1 周
第 1 月         75%          中            1 月
第 3 月         90%          高            3 月+
第 6 月         95%+         极高          几乎不可能
```

越用越精准 → 用户越依赖 → 迁移成本越高 → 竞品越难追赶。品味画像是用户的**数据资产**，不是产品的功能。

## 4. 系统架构

### 4.1 架构原则

1. **系统驱动，不是用户驱动**：核心是 Cron daemon，不是 Web 请求响应
2. **单 Agent + 多 Tool**：基于 Claude Code 源码分析，放弃 CrewAI 多 Agent 架构
3. **无状态 Agent Loop**：每次 Pipeline 执行启动新的 agent loop，品味画像通过 system prompt 注入
4. **异步通知为主交互**：用户通过飞书/微信接收通知，不需要打开后台
5. **渐进式扩展**：先跑通单平台，再扩展多平台

### 4.3 Agent Loop Core

基于 Claude Code 源码分析（query.ts 的 1729 行核心循环），TasteCraft 的 agent loop 精简为约 100 行 Python：

```python
async def agent_loop(
    system_prompt: str,
    tools: list[Tool],
    initial_message: str,
    max_turns: int = 20,
) -> AgentResult:
    """
    核心 agent 循环。每次 Pipeline 执行时启动一个新的 loop。
    无状态设计——品味画像通过 system_prompt 注入。
    """
    client = AsyncAnthropic()
    messages = [{"role": "user", "content": initial_message}]
    tool_schemas = [t.to_anthropic_schema() for t in tools]

    for turn in range(max_turns):
        response = await client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=8192,
            system=system_prompt,
            messages=messages,
            tools=tool_schemas,
        )

        messages.append({"role": "assistant", "content": response.content})
        tool_uses = [b for b in response.content if b.type == "tool_use"]

        if not tool_uses:
            text = "".join(b.text for b in response.content if b.type == "text")
            return AgentResult(success=True, output=text, turns=turn + 1)

        tool_results = []
        for tu in tool_uses:
            tool = find_tool(tools, tu.name)
            try:
                result = await tool.execute(**tu.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": tu.id,
                    "content": json.dumps(result, ensure_ascii=False),
                })
            except Exception as e:
                logger.error(f"Tool {tu.name} failed: {e}")
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": tu.id,
                    "content": f"Error: {e}",
                    "is_error": True,
                })

        messages.append({"role": "user", "content": tool_results})

    return AgentResult(success=False, output="Max turns exceeded", turns=max_turns)
```

### 4.4 架构决策记录（ADR）

**ADR-001: 放弃 CrewAI，改用 Anthropic SDK 单 Agent Loop**

- 背景：原方案使用 CrewAI 6 Agent 架构
- 问题：CrewAI 引入 3-4 层抽象，agent 间通信脆弱，调试困难
- 决策：改用 Anthropic SDK 的 messages.create() + tool_use 循环
- 依据：基于 Claude Code 源码分析，其核心也是一个 while(true) + tool_use 循环
- 后果：代码量从 ~3000 行降至 ~500 行，LLM 调用次数从 6+/篇降至 1-2/篇，成本降低 ~70%

**ADR-002: 系统驱动（Cron daemon），不是用户驱动（Web app）**

- 背景：原方案是用户通过 Web 界面或 CLI 手动触发
- 决策：核心是 7x24 运行的 Cron daemon，用户通过异步通知交互
- 后果：用户从"内容生产者"变成"内容策略制定者"，每天只需 5-15 分钟

**ADR-003: 品味画像通过 System Prompt 注入，不是 RAG**

- 背景：有两种方案让 Claude 了解用户品味——RAG 检索 vs 直接注入 system prompt
- 决策：品味画像 JSON 直接作为 system prompt 的一部分（通常 <2000 tokens）
- 后果：简单、可靠、可调试；如果画像超过 4000 tokens，考虑摘要压缩

### 4.5 Pipeline 与 Agent Loop 的关系

每个 Pipeline = 一次 Agent Loop 调用：

```
Content Pipeline:
  agent_loop(
    system_prompt = base_prompt + taste_profile + today_trending,
    tools = [research_tool, write_tool, review_tool, adapt_tool],
    message = "根据品味画像和今日热点，为以下平台生成内容：{platforms}"
  )

Publish Pipeline:
  直接调用 Playwright 工具，不需要 LLM（除非发布失败需要诊断）

Analytics Pipeline:
  agent_loop(
    system_prompt = base_prompt + taste_profile,
    tools = [collect_analytics, update_profile],
    message = "采集以下内容的平台数据并分析：{content_ids}"
  )

Evolution Pipeline:
  agent_loop(
    system_prompt = evolution_prompt + taste_profile + weekly_data,
    tools = [update_taste_profile, generate_report],
    message = "分析本周数据，更新品味画像，生成进化报告"
  )
```

## 6. Pipeline 详细设计

### 6.1 Content Pipeline（内容生产线）

**触发**: 每日 09:00 | **耗时**: ~3-5 分钟 | **输出**: 1-3 篇待发布内容

```
步骤 1: 加载上下文
  → 读取用户品味画像
  → 读取今日赛道热点（trending_cache）
  → 读取最近 7 天发布记录（避免重复选题）

步骤 2: Agent Loop 执行
  Tools: research_trending, generate_content, self_review, adapt_for_platform
  Message: "今天需要为以下平台各生成一篇内容：{platforms}。
            请先研究今日热点，结合品味画像选题，然后生成、审核、适配。"

步骤 3: 质量门控
  → 自审评分 >= 70：自动入队
  → 自审评分 50-70：标记需人工确认，通知用户
  → 自审评分 < 50：丢弃，尝试重新生成（最多 2 次）

步骤 4: 入队
  → 根据各平台最佳发布时间，设定 scheduled_at
  → 写入 content_queue
```

**质量自审标准：**

| 维度 | 权重 | 评分规则 |
|------|------|---------|
| 品味一致性 | 30% | 与画像的调性、用词、禁忌的符合程度 |
| 内容原创性 | 20% | 非模板化内容、有独特观点或案例 |
| 平台适配度 | 20% | 长度、格式、标签符合平台规范 |
| Hook 吸引力 | 15% | 开头 3 句是否有吸引力 |
| 可读性 | 15% | 段落节奏、逻辑清晰度 |

### 6.1.1 三种内容生成模式

Content Pipeline 支持三种生成模式，覆盖从纯自动到深度协作的完整光谱。用户可在 Onboarding 时设定默认模式，也可按单篇内容切换。

#### Mode A：托管模式（Autopilot）

**定位**：保底模式，零人工介入，系统全权负责，最大化产出效率。当用户无暇参与或 Mode B 超时降级时自动启用。

> **风险警示**：Mode A 的品味进化信号最弱（无用户修改数据），长期依赖会导致品味画像停滞。
> 此外，爆款复刻策略存在平台风控风险——各平台持续升级原创检测算法（语义指纹、感知哈希），
> 内置查重 tool 与平台检测逻辑可能存在偏差。建议 Mode A 仅作为产出量补充，不作为主力模式。

**核心策略：爆款启发式创作 + 原创性保障**

系统基于已验证的爆款内容**提取可复用的模式**（结构、句式框架、情绪节奏），结合品味画像生成原创内容。重点是"学习爆款的方法论"而非"复制爆款的文字"。

```
流程：
  1. 爆款素材库构建
     → 从 trending_cache 中筛选本赛道近 7 天 Top 20 爆款
     → 提取每篇爆款的：标题句式、开头 hook、段落结构、金句原话、话题标签
     → 按平台分类存入 reference_pool

  2. 内容生成（爆款复刻）
     → Agent 从 reference_pool 选择 1-3 篇高相关爆款作为参考
     → 生成策略：
        - 标题：复用爆款句式，替换关键词（"试了20款AI工具" → "试了15款效率神器"）
        - 开头：保留爆款的 hook 结构，替换具体场景
        - 正文：复用段落节奏和论证结构，替换案例和数据
        - 金句：尽量保留爆款原话中的高传播句式，微调用词
        - 结尾：复用 CTA 模式（引导互动/收藏/关注）

  3. 查重规避处理
     → 文本层面：同义词替换、句式重组、段落顺序调整
     → 语义层面：保留核心观点，更换论据和案例
     → 结构层面：保留信息密度，调整小标题和分段方式
     → 目标：与原文相似度 < 30%（通过内置查重 tool 验证）

  4. 图片处理
     → 从爆款内容提取配图风格（构图、色调、文字排版）
     → 生成同风格但不同内容的配图（调用图片生成 tool）
     → 封面图：复刻爆款封面的排版模式（大字标题+背景色块），替换文案
     → 内文配图：保持相似的信息图/截图风格，替换具体数据
     → 图片查重：对生成图片做像素级微调（轻微裁剪、色调偏移、加噪点）

  5. 质量门控 → 入队发布
```

**适用场景**：
- 用户完全信任系统，追求最大产出量
- 已有成熟品味画像（置信度 >= 0.7）
- 赛道内容同质化程度高、爆款模式明确的领域（如种草、测评、清单类）

**输出物**：完整的图文内容，直接入队发布，无需用户介入。

#### Mode B：协作模式（Co-Create）

**定位**：默认推荐模式。AI 做 80% 的工作，用户补齐 AI 做不到的 20%——真实体验、实拍素材、个人故事。每次协作都是高质量的品味进化信号。

**核心策略：AI 搭框架 + 用户填血肉**

```
流程：
  1. AI 先行阶段（自动完成，无需用户介入）
     → 选题研究：基于热点+品味画像确定选题方向
     → 内容框架：生成完整的内容大纲（标题、段落结构、每段要点）
     → 可自动化部分先写好：
        - 背景介绍、行业数据、趋势分析（AI 擅长）
        - 话题标签、SEO 关键词（AI 擅长）
        - 结尾 CTA、互动引导（AI 擅长）
     → 标记需要用户补齐的"空位"（slot）

  2. 用户协作请求（通过飞书/微信通知）
     → 系统发送协作请求，明确告诉用户需要补什么：

     ┌─────────────────────────────────────────────┐
     │  TasteCraft 协作请求                          │
     │                                               │
     │  选题：「我用 XX 产品一个月的真实体验」         │
     │  平台：小红书                                  │
     │                                               │
     │  AI 已完成：                                   │
     │  ✅ 标题（3 个备选）                           │
     │  ✅ 开头 hook                                  │
     │  ✅ 产品背景介绍                               │
     │  ✅ 话题标签 + SEO                             │
     │  ✅ 结尾互动引导                               │
     │                                               │
     │  需要你补齐：                                  │
     │  📸 拍 3-5 张产品实拍图（建议角度：开箱/使用中/效果对比）│
     │  ✏️ 写 2-3 句你的真实使用感受（不用长，口语化即可）│
     │  📝 确认/修改 AI 写的产品优缺点是否准确         │
     │                                               │
     │  [查看完整草稿] [上传素材] [跳过，全自动发布]    │
     └─────────────────────────────────────────────┘

  3. 素材整合
     → 用户上传照片/文字后，AI 自动整合到内容中
     → 照片：自动调整尺寸、加滤镜（匹配品味画像的视觉风格）、排序
     → 用户文字：保留原话风格，AI 只做衔接和排版，不改写用户原话
     → 生成最终版本 → 发送预览给用户

  4. 用户确认
     → 用户确认发布 / 要求修改 / 放弃
     → 超时处理：24 小时未响应 → 自动降级为 Mode A 全自动发布
```

**Slot 类型定义**：

| Slot 类型 | 说明 | 示例 |
|-----------|------|------|
| `photo_required` | 需要用户拍摄/上传实拍照片 | "拍 3 张产品使用场景照" |
| `experience_required` | 需要用户写真实体验/感受 | "写 2-3 句你的真实使用感受" |
| `fact_check` | 需要用户确认事实准确性 | "确认这个价格/参数是否正确" |
| `choice_required` | 需要用户在多个方案中选择 | "选一个你最喜欢的标题" |
| `context_required` | 需要用户补充背景信息 | "这个项目的具体成果数据是？" |

**飞书/微信通知精简规范**：

飞书消息卡片有 28KB 限制，且用户在手机上注意力极短。协作请求通知必须遵循：

```
规则：
  1. 通知正文 ≤ 3 行，只说"要什么"，不说"AI 做了什么"
  2. 一个主按钮（"上传素材"）+ 一个次按钮（"跳过"）
  3. 详情页通过按钮跳转，不在通知里展开

精简版通知模板：
  ┌──────────────────────────────────┐
  │  📝 「XX产品真实体验」需要你补充    │
  │  📸 拍 3 张实拍图 + ✏️ 写 2 句感受  │
  │  ⏰ 24h 内未回复将自动发布           │
  │                                    │
  │  [上传素材]  [跳过，直接发布]        │
  └──────────────────────────────────┘

完整草稿、AI 已完成的部分、详细建议 → 点击"上传素材"后在详情页展示
```

**适用场景**：
- 个人体验类内容（测评、日记、心得）
- 需要真实素材增强可信度的内容
- 用户有一定参与意愿但时间有限（每篇 5-10 分钟）

**输出物**：AI 框架 + 用户素材的混合内容，经用户确认后发布。

        │  转场：快速缩放                                │
        │                                               │
        │  [00:45-00:55] 反转/高潮                       │

        │  台词："直到我发现了这个方法..."                │
        │                                               │

        │  画面：对着镜头                                │
        │  台词："关注我，下期教你具体怎么做"              │
        │  字幕：引导关注+评论                            │
        └─────────────────────────────────────────────┘

    1.3 多轮打磨（用户交互）
        → 发送脚本给用户，附带修改引导：

        ┌─────────────────────────────────────────────┐
        │  脚本审阅请求                                  │
        │                                               │
        │  AI 为你写了一个 60s 短视频脚本，请审阅：       │
        │                                               │
        │  [查看完整脚本]                                │
        │                                               │
        │  请重点关注：                                  │
        │  1. 台词是否像你平时说话的风格？                │
        │  2. 有没有你说不出口的句子？                    │
        │  3. 场景设定是否可行（你能拍到这些画面吗）？     │
        │                                               │
        │  [台词风格 OK] [需要调整台词] [场景不可行]      │
        │  [整体方向不对，换个思路]                       │
        └─────────────────────────────────────────────┘

        → 根据用户反馈修改脚本，最多 3 轮交互
        → 每轮只改用户指出的问题，不主动大改
        → 最终版本需用户明确确认："这版可以拍了"

  Phase 2: 用户录制（用户主导，AI 辅助）

    2.1 录制指南生成
        → 基于最终脚本，自动生成录制指南：

        ┌─────────────────────────────────────────────┐
        │  录制指南                                     │
        │                                               │
        │  设备：手机竖屏拍摄即可                         │
        │  光线：自然光 or 台灯补光，避免逆光              │
        │                                               │
        │  需要录制的片段：                               │
        │  📹 片段 1：口播开场（5s）                     │
        │     - 对着镜头说 hook 台词                     │
        │     - 表情自然，不用太严肃                      │
        │                                               │
        │  📹 片段 2：屏幕录制（20s）                    │
        │     - 打开 XX 软件，展示操作流程                │
        │     - 可以用手机录屏功能                        │
        │                                               │
        │  📹 片段 3：口播主体（20s）                    │
        │     - 不用一字不差背台词，说大意即可             │
        │     - 多录几遍，AI 会选最好的                   │
        │                                               │
        │  📹 片段 4：成果展示（10s）                    │
        │     - 截图/实物展示                             │
        │                                               │
        │  📹 片段 5：口播结尾（5s）                     │
        │     - CTA 台词                                │

        │  - 每个片段多录 2-3 遍，给 AI 剪辑选择空间     │

        │  - 录完直接上传，不用自己剪                     │
        │                                               │
        │  [开始上传素材]                                │
        └─────────────────────────────────────────────┘

    2.2 素材上传
        → 用户通过飞书/Web/CLI 上传录制的视频片段
        → 支持批量上传，自动按时间排序
        → 上传后系统自动开始 Phase 3

  Phase 3: AI 后期制作（后续增强，非 MVP 范围）

    > **MVP 阶段**：用户录制完成后，自行使用剪映/CapCut 等工具剪辑。
    > TasteCraft 的 MVP 价值在于脚本创作环节——这已经足够有价值。
    > AI 剪辑能力推迟到 Phase 5+ 实现，届时技术成熟度更高。

    3.1 素材分析（Phase 5+）
        → 对每个片段进行：语音转文字、画面质量评估、情绪识别
        → 从多条录制中选择最佳 take（画面稳定、语音清晰、表情自然）
        → 标记可用片段和需要补录的片段

    3.2 自动剪辑
        → 按脚本时间线拼接最佳片段
        → 添加：字幕（基于语音转文字）、BGM、转场效果、封面
        → 字幕风格匹配品味画像（字体、颜色、位置）
        → BGM 从免版权音乐库中匹配（节奏、情绪）

    3.3 成品预览
        → 生成预览视频 → 发送给用户

        ┌─────────────────────────────────────────────┐
        │  视频成品预览                                  │
        │                                               │
        │  「AI 创业者的一天」 | 58s | 抖音               │
        │                                               │
        │  [播放预览]                                    │
        │                                               │
        │  AI 处理详情：                                 │
        │  ✅ 使用了片段 1 的第 2 遍录制（最自然）        │
        │  ✅ 片段 3 拼接了两遍录制的最佳部分             │
        │  ✅ 添加了 12 条字幕                           │
        │  ✅ BGM：「Morning Coffee」 轻快风格            │
        │  ⚠️ 片段 2 的屏幕录制略模糊，建议重录          │
        │                                               │
        │  [确认发布] [需要修改] [重新剪辑] [补录素材]    │
        └─────────────────────────────────────────────┘

    3.4 用户审核 → 发布
        → 用户确认后入队发布
        → 如需修改：用户标注具体时间点和问题 → AI 重新剪辑该段
        → 最多 2 轮修改，之后建议用户手动微调或接受当前版本
```

**技术依赖**：

| 能力 | 技术方案 | 优先级 | 阶段 |
|------|---------|--------|------|
| 脚本生成 | Claude API + 品味画像 | P0 | MVP（Phase 3） |
| 多轮打磨交互 | 飞书消息卡片 | P0 | MVP（Phase 3） |
| 录制指南生成 | 模板引擎 | P0 | MVP（Phase 3） |
| 语音转文字 | Whisper API / 阿里云 ASR | P1 | Phase 5+（AI 剪辑） |
| 视频剪辑 | FFmpeg + MoviePy | P1 | Phase 5+（AI 剪辑） |
| 字幕生成 | ASR 结果 + 时间轴对齐 | P1 | Phase 5+（AI 剪辑） |
| BGM 匹配 | 免版权音乐库 + 情绪标签匹配 | P2 | Phase 5+（AI 剪辑） |
| 画面质量评估 | 多模态模型（Gemini Pro Vision 级别） | P2 | Phase 5+（AI 剪辑） |
| 封面生成 | 关键帧提取 + 文字叠加 | P2 | Phase 5+（AI 剪辑） |

> **注意**：AI 剪辑中"从多条录制中选择最佳 take"需要视频理解能力（画面稳定性+表情自然度+语音清晰度的综合判断），
> 简单的 OpenCV 模糊检测不够，需要多模态模型支持。这是推迟到 Phase 5+ 的主要技术原因。

**适用场景**：
- 抖音、B站、视频号等视频优先平台
- 用户愿意出镜但不会剪辑
- 个人 IP 类内容（口播、vlog、教程）

**输出物**：完整的短视频（含字幕、BGM、封面），经用户审核后发布。

#### 三种模式的对比与选择

| 维度 | 托管模式（Mode A） | 协作模式（Mode B） | 导演模式（Mode C） |
|------|-------------------|-------------------|-------------------|
| 面向用户的名称 | "全交给 AI" | "AI + 你" | "你出镜，AI 制作" |
| 用户时间投入 | 0 分钟 | 5-10 分钟/篇 | 30-60 分钟/篇（含录制） |
| 内容类型 | 图文 | 图文 | 短视频 |
| 个人辨识度 | 低（AI 风格为主） | 中（真实素材加持） | 高（用户出镜+个人风格） |
| 平台查重风险 | 中（依赖原创性保障） | 低（有原创素材） | 极低（原创录制） |
| 适用平台 | 小红书、微博、知乎 | 小红书、微信公众号、知乎 | 抖音、B站、视频号 |
| 实现优先级 | P0（Phase 0） | P0（Phase 1） | P2（Phase 3+） |
| 品味进化信号 | 弱（无用户修改） | 强（用户素材+修改） | 强（多轮脚本打磨） |

**默认模式推荐逻辑**：

```
if 平台 in [抖音, B站, 视频号]:
    推荐 导演模式（Mode C）
elif 品味画像.confidence >= 0.7 and 用户明确选择 == "全自动":
    使用 托管模式（Mode A）
else:
    推荐 协作模式（Mode B）  # 默认走协作，最大化品味进化信号

# 用户可随时覆盖默认推荐
# 关键原则：Mode B 是默认模式，Mode A 是保底/降级模式
```

**模式间的降级/升级**：

- Mode B 超时未响应（24h）→ 自动降级为 Mode A
- Mode C 用户放弃录制 → 降级为 Mode B（图文版本）或 Mode A
- Mode A 连续 3 篇互动率低于均值 0.5x → 系统自动建议升级为 Mode B（增加真实素材）
- Mode A 连续使用 7 天无任何用户交互 → 发送提醒："协作模式能让内容更像你，要试试吗？"

**跨模式数据流**：

```
Mode A 高表现内容 ──→ 自动加入 Mode B/C 的参考素材库
                      （爆款模式可被协作模式复用）

Mode B 用户素材+修改 ──→ 品味画像强信号
                         （用户原话风格、照片审美偏好）

Mode C 脚本打磨记录 ──→ 品味画像强信号
                         （台词风格偏好、场景可行性约束）
                    ──→ Mode B 的写作风格参考
                         （用户确认的台词 = 最真实的个人表达）

所有模式的平台数据 ──→ 统一进入 Evolution Pipeline
                      （不区分模式来源，按信号强度加权）
```

### 6.2 Publish Pipeline（发布线）

**触发**: 每日 12:00 / 18:00 / 21:00 | **耗时**: ~1-2 分钟/平台

```
步骤 1: 从队列取内容（scheduled_at <= NOW() AND status = 'pending'）
步骤 2: 逐平台发布（每个平台独立执行，互不阻塞）
步骤 3: 发布前检查 Cookie/Token 有效性（失效则跳过+通知用户）
步骤 4: 记录结果（成功→更新 published_at；失败→retry_count += 1）
步骤 5: 超过 3 次重试→标记 failed→通知用户
```

**发布间隔策略：**
- 同一平台两次发布间隔 >= 30 分钟
- 不同平台可并行发布
- 模拟人工操作节奏（随机延迟 2-5 秒）

### 6.3 Analytics Pipeline（数据回收线）

**触发**: 每日 23:00 | **耗时**: ~2-3 分钟

```
采集目标：
  T+24h：昨天发布的内容
  T+72h：3 天前发布的内容（补采稳定数据）
  T+7d：7 天前发布的内容（最终数据）

采集方式：
  登录平台创作者后台（Playwright/CDP）→ 定位到对应内容 → 抓取数据指标

衍生计算：
  engagement_rate = (likes + comments + saves + shares) / views
  与历史均值对比，标记异常值（高于均值 2x 或低于均值 0.5x）
```

### 6.4 Evolution Pipeline（品味进化线）

**触发**: 每周日 22:00 | **耗时**: ~5-10 分钟

```
步骤 1: 汇总本周数据
  → 本周生成/发布数量
  → 各平台数据汇总
  → 用户修改记录汇总
  → 表现最好/最差的 3 篇内容

步骤 2: Agent Loop 执行（使用进化 Prompt）
  → Claude 分析所有信号
  → 输出需要调整的维度（最多 3 个）
  → 每个调整附带原因、置信度、是否试探性

步骤 3: 更新品味画像
  → 创建新版本画像（version += 1）
  → 旧版本标记 is_active = false
  → 记录 evolution_log

步骤 4: 生成周报 → 发送给用户
```

### 6.5 Trending Pipeline（赛道热点扫描）

**触发**: 每周一 09:00 | **耗时**: ~5 分钟

根据用户品味画像的 topics 确定赛道关键词 → 搜索各平台近 7 天爆款内容 → Claude 分析爆款共性特征 → 写入 trending_cache（7 天过期）。

4. 指纹隔离：每个平台使用独立的浏览器 profile
5. IP 策略：默认使用本机 IP，不使用代理
6. 异常检测：如果连续 3 次发布失败，暂停该平台 24 小时

## 8. 产品形态与用户交互

### 8.1 产品形态决策

**核心交互载体：响应式 Web App（PWA）**

TasteCraft 的主交互界面是一个响应式 Web 应用，桌面和手机共用一套代码。通知渠道（飞书/微信/Telegram）是可选的辅助触达方式，不是核心交互入口。

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| 原生 App（iOS + Android） | 推送体验好、离线能力强 | 双端开发成本高、审核周期长、更新慢 | 排除 |
| 响应式 Web App（PWA） | 一套代码跨平台、与现有 React+Vite 技术栈一致、即时更新、可添加到主屏幕 | 推送能力弱于原生（iOS 限制） | **选定** |
| 飞书/微信 Bot 为主 | 开发成本最低 | 交互能力受限、无法承载复杂操作（品味编辑、内容预览、数据看板） | 降级为通知渠道 |

**技术选型**：React + Vite + TailwindCSS + PWA（Service Worker + Web App Manifest）

```
用户日常接触 TasteCraft 的方式：
  60%  Web Dashboard（内容管理、品味编辑、数据看板、Onboarding）
  25%  推送通知（飞书/微信/浏览器推送，可选配置）
  10%  CLI 命令（高级用户、开发调试）
  5%   API（第三方集成）
```

### 8.4 Onboarding 闯关系统

> **核心洞察**：协作模式的冷启动期（前 2 周）如果没有正向反馈循环，用户会在第一周就流失。
> 必须通过游戏化引导让用户在"起号期"保持参与感，同时管理好"半个月没流量是正常的"的心理预期。

#### 8.4.1 闯关设计

Onboarding 分为 5 个关卡，每个关卡有明确的完成条件和奖励反馈。用户在 Dashboard 首页看到闯关进度条。

```

│                                                            │
│  ████████░░░░░░░░░░░░  第 2 关 / 共 5 关                   │
│                                                            │
│  ✅ 第 1 关：建立你的品味档案                               │
│  🔵 第 2 关：发布你的第一篇内容        ← 当前              │
│  ⬜ 第 3 关：完成第一次协作                                 │
│  ⬜ 第 4 关：坚持 7 天                                     │
│  ⬜ 第 5 关：收获第一个正反馈                               │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

**第 1 关：建立你的品味档案**（预计 5 分钟）

```
任务清单：
  [ ] 完成品味问卷（5 个问题）或导入已有内容
  [ ] 选择目标平台（至少 1 个）
  [ ] 登录至少 1 个平台账号（Cookie 认证）

  → 系统立即生成第一篇内容预览
  → 展示品味画像可视化（"这就是 AI 眼中的你"）
  → 解锁第 2 关
```

**第 2 关：发布你的第一篇内容**（预计 10 分钟）

```
任务清单：
  [ ] 预览 AI 生成的第一篇内容
  [ ] 修改或确认内容（鼓励修改——"你的修改会让 AI 更懂你"）
  [ ] 点击发布

完成奖励：
  → 🎉 "你的第一篇内容已上线！"
  → 展示发布链接（可直接跳转查看）
  → 提示："24 小时后我们会告诉你数据表现"

```

**第 3 关：完成第一次协作**（预计 10 分钟）

```
任务清单：
  [ ] 收到协作请求通知
  [ ] 上传至少 1 张实拍照片 或 写至少 1 句真实感受

完成奖励：
  → "有你的真实素材，这篇内容的辨识度提升了 40%"
  → 展示"AI 版本 vs 协作版本"的对比（让用户看到差异）
  → 解锁第 4 关
```

**第 4 关：坚持 7 天**（预计 7 天）

```
任务清单：
  [ ] 连续 7 天有内容发布（托管模式自动发布也算）
  [ ] 至少参与 3 次协作（上传素材或修改内容）

完成奖励：

```

  [ ] 任意一篇内容阅读量 >= 500

> **关键原则**：在用户看到数据之前，就告诉他"没数据是正常的"。不要等用户失望了再安慰。

**Onboarding 时的预期设定**（第 1 关完成后展示）：

```
┌─ 起号须知 ──────────────────────────────────────────────┐

│  → 重点不是数据，是让 AI 学习你的风格                     │
│                                                          │
│  第 3-4 周：萌芽期                                       │

│  → 品味画像趋于成熟，内容质量明显提升                     │

│  → 内容修改率大幅下降（AI 越来越像你）                    │

### 14.4 品味进化引擎：混合架构决策

**决策：保留现有数学模型 + 新增 LLM 推理层，双层协作。**

理由：
- 现有 taste_engine.py 的数学模型（时间衰减+三因素加权+对数置信度增长）在信号充足时表现稳定
- LLM 推理在冷启动阶段和模式识别（如"用户总是删除某个词"）上更强
- 两层互补，而非替代

```
混合架构：
  Layer 1（数学模型）：
    - 信号聚合：TasteSignal → TasteVector
    - 时间衰减：近期信号权重更高
    - 置信度计算：对数增长曲线
    - 输出：量化的维度调整建议

  Layer 2（LLM 推理）：
    - 输入：Layer 1 的量化建议 + 原始信号数据
    - 分析：模式识别、因果推理、趋势预测
    - 输出：自然语言的进化报告 + 最终画像 JSON
    - 约束：不能覆盖 Layer 1 的高置信度结论

  合并逻辑：
    - Layer 1 置信度 >= 0.7 → 直接采纳，LLM 只生成解释文本
    - Layer 1 置信度 0.3-0.7 → LLM 参与决策，可调整方向
    - Layer 1 置信度 < 0.3 → LLM 主导决策（冷启动场景）
```
